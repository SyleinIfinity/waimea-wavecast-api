# TL08-C — Production forward forecasts and NOAA evaluation

Status: **ENABLED_IN_PRODUCTION; 30-minute live evaluation and training snapshot verified** (2026-11-13 UTC). This pipeline uses actual NOAA, Cloud SQL and private GCS on the VM. It is not fixture/demo output. All source models remain DRAFT/NOT_READY. Forecasts are explicitly `experimental` and separate from approved `gold.predictions`.

## Architecture and schedule

`waimea-forward-forecast.timer` runs a bounded Compose one-off worker every five minutes. The worker first recovers DB reservations missing GCS finalization, reconciles QC truth, exports verified training examples, then issues new 30-minute, 1-day and 7-day forecasts. `waimea-forward-retrain.timer` runs Sunday 04:00 UTC; it only fits new DRAFT models after at least 300 matched 30-minute examples or 180 matched examples for a daily horizon. It never auto-promotes or swaps an active model. Both timers are enabled and persist across reboot; the four core Backend services and historical timer remain separate.

The 30-minute *issued* forecast uses model 17, trained to predict 90 minutes after its latest observed input. NOAA commonly publishes that input 25–60 minutes late; the worker only issues when the exact target timestamp is still 15–45 minutes in the future. It refuses retrospective nowcasts. This means some cycles legitimately issue no 30-minute forecast. Model 8 predicts the next HST day's median WVHT; model 11 predicts the median of the HST day seven dates after the anchor. Both require seven contiguous Daily Features with QC-valid observed data and matching `GOLD_READY` daily Gold metrics. The actual lead from issuance is recorded in `issued_at` and `target_at`.

## Persistence and correction handling

Migration 11 adds `gold.forward_forecasts`, `gold.forward_evaluations` and `gold.forward_training_examples`; migration 12 adds lead-time eligibility to the training view. A forecast is reserved in PostgreSQL before its target, uploaded once to `gs://waimea-noaa/predictions/forward/`, downloaded by pinned generation and byte-verified, then finalized. Retry uses the same reserve and immutable object. A correction creates a new evaluation event; the forecast itself is never changed. The training view exposes only the latest QC-verified actual outcome for each finalized forecast with operational lead time (30min: 15–45 minutes; 1d: over 20 hours; 7d: over one day). Late forecasts remain auditable but do not contribute to training or skill metrics. Prediction values are retained for error analysis but **never used as training labels**. Each changed training-example snapshot is versioned by SHA-256 in private GCS.

The Database API's private `/internal/v1/forward/reconcile` verifies exact Silver WVHT and Gold `GOLD_READY` for 30-minute targets. Daily truth uses a completed `GOLD_READY` Gold daily median computed after that HST day ended. It records absolute error, squared error, persistence error and a truth fingerprint. The worker scans recent targets every cycle and a 90-day correction window once daily. Public `GET /api/v1/forecasts/experimental/latest` exposes only lead-eligible forecast/result fields with the experimental label; private metrics and training-example endpoints require the internal token.

## Remaining validation and limitations

The 30-minute live evaluation and GCS training-example export are verified. The 1d forecast 39 and 7d forecast 40 have future target periods, so their live evaluations remain pending. A 30-minute forecast appears only when NOAA publication latency leaves a true future target. The quality of these draft models remains experimental; model 17 was slightly worse than persistence in retrospective MAE. The weekly retrainer cannot run meaningfully until at least 300 matched short examples or 180 daily examples accumulate. Retrained models will stay DRAFT pending independent validation and explicit promotion.

Continue monitoring daily and seven-day evaluations as their target HST days complete. Observe corrections by appending a new truth version; do not rewrite an issued forecast. Rollback: disable both forward timers, leave migration 11/12 data intact, and restore the previous API image if required. The core ingestion scheduler and history reconciler remain independent.
